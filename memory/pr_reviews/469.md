### F15: Same-episode download starts are not atomically claimed  (decided)

- **severity:** Warning
- **architecture:** true
- **confidence:** high
- **location:** PodHaven/Cache/CacheManager.swift:114
- **scope:** related
- **concern:** downloadToCache reads cacheStatus and creates/resumes a task before any atomic per-episode claim prevents a second same-episode caller from doing the same.
- **issue:** concurrent callers that both read uncached can each create a URLSession task before updateDownloading(true) is visible.
- **impact:** duplicate background downloads waste bandwidth/battery and can let the first terminal callback resolve awaiters while another same-episode task is still running.
- **recommendation:** claim the episode for download atomically, or serialize starts per episode until the DB flag/live task is visible, before creating/resuming a background task.
- **test_plan:** gate two same-episode callers before the claim and assert only one download task is created.
- **status:** decided
- **decision:** open follow-up issue — pre-existing in main (downloadToCache body byte-identical to main; both observer call sites predate the PR), and the only novel impact (premature nil to awaiters) rides on the await API, which has no production consumer (split from #461). An atomic claim also restores the single-in-flight premise the F5 skip relied on, without closing F5's sequential µs-window residual (needs attempt-scoped signaling).
- **follow_up_issue:** jubishop/podhaven#483
