## Findings

### F1: Concurrent same-episode awaiters can deadlock  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Cache/CacheManager.swift cachedURL/signalDownloadComplete
- **concern:** cachedURL defer removed the shared latch on any return, orphaning a still-waiting concurrent caller's latch
- **resolution:** refcounted DownloadLatch (waiters count) keeps the shared latch registered until the last awaiter leaves; signalDownloadComplete reads entry.latch. Regression test cancelledAwaiterDoesNotStrandConcurrentAwaiter (red on old code, green after).
- **fixed_at:** 2026-06-14

### F2: reconcileStaleDownloads not awaited before observations start  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Cache/CacheManager.swift start()/reconcileStaleDownloads
- **concern:** start() fired reconcile as a detached Task racing the currentEpisode observer, so a stranded download could be skipped as "already caching" then reconciled away
- **resolution:** reconcileStaleDownloads is now async and awaited before the observers subscribe (one ordered Task in start()). Regression test resumesStrandedCurrentEpisodeOnStart (red on old code, green after).
- **fixed_at:** 2026-06-14
- **source_thread_id:** PRRT_kwDONT4Ems6Jc3yU

### F4: temp-move failure in non-async didFinishDownloadingTo skips the latch signal  (fixed)

- **severity:** Nit
- **status:** fixed
- **location:** PodHaven/Cache/CacheBackgroundDelegate.swift didFinishDownloadingTo (non-async)
- **concern:** the non-async override returned on moveItem failure before scheduling the async work, so the defer-based completion signal never ran and an awaiter could hang
- **resolution:** signal completion in the catch (via episodeID(for:)) before returning. No regression test: the fake's finishDownload invokes the async delegate method directly, so the non-async override is never exercised by the harness.
- **fixed_at:** 2026-06-14

### F5: Cross-attempt latch resolution — stale callback resolves a newer attempt early  (skipped)

- **severity:** Warning
- **architecture:** true
- **status:** skipped
- **location:** PodHaven/Cache/CacheManager.swift:62-69
- **concern:** downloadLatches is episode-keyed, so in principle attempt-1's terminal callback can open+remove attempt-2's latch
- **resolution:** comment corrected to drop the false "can never resolve a later one" guarantee and state the single-in-flight-attempt-per-episode assumption. The race is left unfixed by author decision (no follow-up): the harmful variant is failure-path only and the signal fires in a synchronous tail right after the flag clears, so a replacement attempt would need attempt-1's thread preempted across two serialized DB writes in a ~µs window — vanishingly rare. If it ever fires (only once #461 adds a consumer), the sole effect is a premature nil from cachedURL; attempt 2 keeps downloading and caches normally, recoverable on retry. No data loss/corruption/stuck state.
- **source_thread_id:** PRRT_kwDONT4Ems6Je2r8

### F7: Move-failure path strands the downloading flag  (fixed)

- **severity:** Warning
- **status:** fixed

### F8: Reattached download after relaunch isn't awaited — premature nil  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Cache/CacheManager.swift cachedURL
- **concern:** downloadLatches is in-memory; a background download reattached after relaunch had a live task but no latch, so cachedURL skipped the wait and returned a premature nil while the download was still in-flight
