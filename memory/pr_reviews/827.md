## Findings

### F1: Handoff and observation can apply queue snapshots out of order  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Cache/CacheManager.swift:110-124, 532-548 (scope: in-diff)
- **concern:** The handoff's database read and the observation's buffered `SharedState` snapshots both replace `currentQueuedEpisodeIDs` without ordering, so an older set applied after a newer one makes an ID "new" again. That retries a just-failed download, or downloads an episode dequeued in the same window.
- **resolution:** Skipped. It needs a dequeue or a download failure within milliseconds of a refresh's end, and costs at most one extra download attempt. `claimForDownloadIfUncached` still blocks concurrent duplicates, and no download is ever missed. Ordering the two sources would need snapshot versioning or a single source of truth. That adds state and test burden this harm doesn't justify.

### F2: Refresh regression test doesn't depend on the handoff  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHavenTests/RefreshSchedulerTests.swift (scope: in-diff)
- **concern:** `backgroundRefreshCachesNewlyQueuedEpisodes` passed with the `runRefresh` handoff removed, so nothing pinned the PR's core claim that downloads are handed off before the background task completes.
- **resolution:** `FakeObservatory` can hold queued-episode deliveries, and `FakeBGTask` takes a completion callback. The test holds the observation and asserts that the download task existed when the task completed.
- **fixed_at:** dfde536e

### F3: New background processes retry every uncached queued episode  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/AppLauncher.swift:144-161 (scope: in-diff)
- **concern:** A queue observation's first snapshot treats every queued ID as new. Starting `CacheManager` in background launches therefore retries each failed, uncached queued download once per new process, not only at a foreground launch.
- **resolution:** Skipped. This is the existing retry-at-start policy reaching the launches the PR targets, and it recovers transient failures. A permanently failing URL costs one request per new process, and the user can dequeue the episode. Tracking failures would add new state.

### F4: Handoff do/catch wraps a non-throwing call  (fixed)

- **severity:** Nit
- **status:** fixed
- **location:** PodHaven/Cache/CacheManager.swift:110-124 (scope: in-diff)
- **concern:** `handOffQueuedDownloads` ran `handleQueueChange` inside its `do`, against the rule to keep `do`/`catch` around `try` calls only.
- **resolution:** The `do` now covers only the latch wait and the database read; `handleQueueChange` runs after it.
- **fixed_at:** dfde536e
