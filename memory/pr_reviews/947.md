### F1: System pauses count as play requests for item-failure intent  (skipped)

- **severity:** Warning
- **architecture:** true
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Events.swift:69 (scope: in-diff)
- **concern:** A route-loss pause or widget route-recovery timeout pause doesn't advance the request revision, so a later non-reset item failure recovers with intent `.play` and can start audio, possibly through the speaker. PR 959 derives the same check separately through `playRequested(by:)`, with an extra auto-advance rule.
- **resolution:** Deferred, not fixed. Same root cause and fix as jubishop/podhaven#957, which now also covers item-failure recovery and one shared check, and is blocked by #880. It needs an item failure while the system has paused playback, which is rare.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/957

### F2: Recovery reload clears stop-after-episode and silence overrides  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Recovery.swift:37 (scope: related)
- **concern:** `stop()` clears the episode's silence overrides and `performLoad` clears `stopAfterCurrentEpisode` on the same-episode recovery reload, so recovered playback continues past the user's stop point. The failed-to-play-to-end path already did this; this PR also sends item failures through it.
- **resolution:** Deferred, not fixed: a pre-existing defect in the shared recovery path, rare (needs both a choice set and a recovered failure), with a design choice about carrying state across the reload.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/961

### F3: Item failure during an auto-advance load reloads the episode paused  (skipped)

- **severity:** Nit
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Events.swift:69 (scope: in-diff)
- **concern:** Between `advance`'s `load` adding observers and its `play(requestID:)`, no play is pending and the player's request is stale, so an item failure there recovers paused.
- **resolution:** The window is a few PlayActor hops; on `main` the same failure stopped playback and moved the episode to Up Next, so this is no worse. The shared check in jubishop/podhaven#957 would cover it.

### F4: Outgoing item failure during a new load cancels the new request  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Events.swift:80 (scope: in-diff)
- **concern:** `handlePlaybackFailure` adopts the current revision, so an outgoing item that fails before the new load removes its observers stops the new request and reloads the old episode.
- **resolution:** On `main`, `stop()` had the same effect. The window spans audio-session configuration and activation, usually milliseconds, and another tap recovers.
