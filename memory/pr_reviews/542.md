## Findings

### F8: Reset outcome inference loses prior failure provenance  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+Events.swift:26-30,180-234
- **concern:** an item failure that clears current identity before reset makes an interrupted reset look idle, suppressing its alert and labeling telemetry `noInterruption`
- **outcome:** queue-only state now emits `queueStateUnknown` while retaining alert suppression; red-green failure-first and idle regressions cover the ambiguity
- **fixed_at:** 2026-07-26

### F7: Failed queue restore can masquerade as a successful resume  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Events.swift:190-258
- **concern:** a failed interrupted-episode unshift can treat a different queued episode as the successful resume target
- **resolution:** the compounded failure is exceptionally rare, and a local outcome/alert guard would improve messaging without restoring the interrupted episode

### F5: Idle reset mislabels the queue as interrupted playback  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+Events.swift:225-263
- **concern:** a stopped reset with no current or loading episode treats any existing Up Next item as interrupted playback and shows a false resume alert
- **outcome:** idle resets with queued episodes now emit `queueStateUnknown` and suppress the resume alert; a red-green regression covers the queue-only path while existing in-flight and OnDeck prompt tests remain green
- **fixed_at:** 2026-07-26

### F6: Resume alert describes the wrong interaction  (fixed)

- **severity:** Nit
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+Events.swift:257-262; PodHaven/Views/UpNext/UpNextView.swift:132-135
- **concern:** the alert says tapping the top Up Next episode resumes playback, but the row tap only opens episode detail
- **outcome:** the alert and incident wording now tell the user to play the episode when ready instead of implying the Up Next row tap starts playback
- **fixed_at:** 2026-07-26

### F4: Cold-launch reset drops the persisted episode  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+Events.swift:179-210; PodHaven/AppLauncher.swift:85-87; PodHaven/Play/PlayManager.swift:167-177
- **concern:** reset clears a persisted currentEpisodeID before OnDeck restoration without returning that episode to Up Next
- **outcome:** reset now falls back to persisted currentEpisodeID, returns it to Up Next without loading or activation, and a red-green cold-launch regression covers the path
- **fixed_at:** 2026-07-26

### F2: Pre-reset automatic workflows can cross the reset boundary  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+Events.swift:176; PodHaven/Play/PlayManager+Recovery.swift:11; PodHaven/Play/PlayManager.swift:167,454
- **concern:** media-services reset cancels only the current load task, so suspended automatic playback workflows can resume after recovery and start a fresh load or play

### F3: Reset can re-log an old load failure  (fixed)

### F1: Reset does not quiesce in-flight playback work  (fixed)

- **status:** fixed
