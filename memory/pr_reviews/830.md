## Findings

### F1: Docs misstate the unavailable window and commit `publishMs`  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** docs/siri-media-playback.md "Commit publication" and diagnostics; PR body; #831
- **concern:** `publishCommits` resets `startedAt` per attempt and lets a superseded attempt finish, so `publishMs` times only the installed attempt and unavailability can reach the burst plus about two attempts. The docs said the burst plus one publication, measured from the run's start, and #831 planned to read `publishMs` as the unavailable time.
- **resolution:** The docs, the PR body, and #831 now say `publishMs` covers only the installed publication and that the window spans the burst plus up to two publications. The per-attempt metric is the right input for #831's faster-publication decision, so the code is unchanged.
- **fixed_at:** 2026-11-04

### F2: Superseded attempts still fetch, encode, and stage the catalog  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Siri/SiriCatalogPublisher.swift `publishCommits(_:)`
- **concern:** A relevant commit that lands mid-attempt doesn't abort it, so each discarded attempt spends a full snapshot fetch, encode, and staged write during a refresh burst.
- **resolution:** Skipped. The shipped path did one full publication per commit and held the writer, so this is strictly less work. Aborting early needs cancellation that the commit observer triggers, which this PR shouldn't add. #831 already decides whether faster publication is warranted.
