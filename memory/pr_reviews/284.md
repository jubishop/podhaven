### F1: Discovery list shows misleading "worked through all picks" empty state after collector reset

- **severity:** Warning
- **architecture:** false
- **confidence:** medium
- **location:** PodHaven/Views/Search/SearchDiscoveryListView.swift:56-69; PodHaven/Views/Search/Models/SearchRecommendationCollector.swift:213-251 (reset); PodHaven/Views/Search/Models/SearchViewModel.swift:662-677 (disappear)
- **description:** `SearchView.onDisappear` calls `viewModel.disappear()` → `recommendationCollector.reset()`, which clears `permanent`/`temporary`/`trendingSourceIndex`/`pickIndex`. A `SearchDiscoveryListView` pushed onto `navigation.search.path` persists across the tab switch (nav path is independent of the collector cache) and reads live `picks(for: source)`, which is now empty, so it renders the empty placeholder "No top picks left / You've worked through all the picks here." TabView tab-switches fire `.onDisappear`, so this is reachable by leaving and returning to Search while a discovery list is pushed. For a **search**-sourced list the picks never return (search isn't re-run on `appear()` — `searchDebouncer.reset()` cleared the query), so it stays falsely "exhausted"; for a **trending** list they repopulate after a multi-second re-fetch, flashing the misleading copy in the meantime.
- **evidence:** SearchView.swift:63 `.onDisappear { viewModel.disappear() }`; SearchViewModel.swift:676 `recommendationCollector.reset()`; SearchDiscoveryListView.swift:21 `picks(for: source)`; placeholder copy "You've worked through all the picks here."
- **impact:** User who opens a discovery list then leaves/returns to the Search tab is told they finished all picks when the cache was actually just cleared — permanently misleading for search lists.
- **recommendation:** When resetting (or in `disappear()`), pop any pushed `.searchDiscovery` destinations from `navigation.search.path` so you never return to a stale list.
- **alternatives:** (a) Gate `reset()` so it doesn't clear while a discovery list is pushed; (b) keep the cache across tab switches and reset only on deinit/memory pressure (also avoids re-fetch+re-embed churn on every Search revisit).
- **test_plan:** A SearchViewModel test that `disappear()` removes `.searchDiscovery` entries from `navigation.search.path` (if fix (a) is chosen). The nav-restoration UI flow itself is hard to unit-test.
- **decision:** Reworked during review (the nav-path splice was rejected as a hack wherever it lived): leaving Search resets its nav stack to root, so Search always reopens at its top level — never a stale pushed view.
- **decision_notes:** User chose the targeted nav-path fix after confirming the deeper refresh-waste (reset() re-runs the full RSS+embed pipeline on every Search return; unsaved-embedding path has no persistent cache) is pre-existing and orthogonal — option 1 doesn't change refresh behavior, only what you see on return. Refresh-waste accepted for now / can be filed separately. Implementation: in `disappear()` (keeps collector free of nav concerns), truncate `navigation.search.path` at the first `.searchDiscovery` case (drop it + any descendants pushed from it); in practice it's at index 0 so this pops to root. Requires `@DynamicInjected(\.navigation)` on SearchViewModel.
- **status:** fixed
- **fixed_at:** 2026-05-31T00:16:00-07:00
- **fix_summary:** `SearchViewModel.disappear()` sets `navigation.search.path = []` (a general "Search opens at its top level" policy — no enum-specific path surgery); injected `\.navigation`. Test `SearchViewModelTests.disappearResetsSearchPathToRoot` (red→green). The selected trending chip persists across the switch (it's `currentTrendingSection` view-model state, not the nav path). Paired with the user-requested typed-search-survival change (see session note + F5).

### F3: Caching a discovery pick removes it in-memory but it resurrects on the next Search visit

- **severity:** Nit
- **architecture:** false
- **confidence:** high
- **location:** PodHaven/Views/Search/Models/SearchRecommendationCollector.swift:802-812 (`isDiscoveryCandidate`); ManagingEpisodes `cacheEpisode`/`saveEpisodeInCache` (call `didPerformAction`)
- **description:** Reframed after investigating the candidate gate. A pick should disappear exactly when the episode stops being a discovery candidate, so the live list matches a fresh reconcile. `isDiscoveryCandidate` excludes on-deck / started (`currentTime != 0`) / finished / rated / queued episodes — but NOT cached ones. play/queue/rate/finish all flip a gate field, so their removal is permanent (✅). But `cacheEpisode`/`saveEpisodeInCache` call `didPerformAction` → `removePick` (in-memory) while changing NO gate field, so on the next Search visit (reset → re-drain → `filteredCandidates`), the cached episode is re-admitted and the pick **reappears**. Materializing the episode gives the podcast a DB row, but it's unsubscribed so reconciliation doesn't drop it. Tagging, by contrast, is already consistent (changes no gate field, doesn't remove, list keeps showing it — matches re-drain). So the original "tagging is inconsistent" framing was wrong; tagging is fine and caching is the real inconsistency.
- **evidence:** `isDiscoveryCandidate` (collector-private, sole discovery gate) checks currentTime/finishDate/rating/queueOrder/on-deck but not `cacheStatus`/`saveInCache`. `Episode.CacheStatus.cached` exists (Episode.swift:332). cacheEpisode/saveEpisodeInCache call `didPerformAction` on success.
- **impact:** A pick the user "dealt with" by caching comes back as a top pick next visit — mildly confusing vanish-then-resurrect. Low user impact.
- **recommendation:** Apply (i): add cache-state to `isDiscoveryCandidate` (exclude `.cached` / save-in-cache episodes) so caching removes-and-stays-gone; keep tagging non-removing. Gate is collector-private, so the change is local.
- **alternatives:** (ii) Stop calling didPerformAction-removal for cache/save so cached picks linger until real engagement.
- **test_plan:** Regression (red before fix): record a source, let a pick land, materialize+cache that episode, re-record/re-drain the source, and assert the cached pick does NOT reappear in `picks(for:)`. Prove it fails on current code (pick resurrects), then passes after the gate change.
- **decision:** Reworked during review: do NOT diverge the discovery gate from canonical `Episode.candidate` (a cached episode still appears in topRecommendations/UpNext). Reverted the gate change; instead make caching non-consuming "like tags" — drop `didPerformAction` from `cacheEpisode`/`saveEpisodeInCache` so pick removal mirrors candidacy exactly.
- **decision_notes:** User agreed cache-state should gate discovery candidacy ("if I've cached it, I've found it"). `Episode.cacheStatus` is `.uncached/.caching/.cached` (derived from `cachedFilename`/`downloading`); `Episode` also exposes a `saveInCache: Bool`.
- **status:** fixed
- **fixed_at:** 2026-05-31T00:16:00-07:00
- **fix_summary:** Reverted the `isDiscoveryCandidate` cache checks (gate back to canonical). Removed the `didPerformAction(episode)` call from `ManagingEpisodes.cacheEpisode` and `saveEpisodeInCache` — the only two non-candidate-breaking actions that fired it; sole `didPerformAction` consumer is `SearchDiscoveryActionsViewModel`. Tests: `candidateGateKeepsCachedEpisodes` (a cached DB row stays a discovery pick) and `cachingDiscoveryPickIsNonConsuming` (drives a real cache to completion via CacheHelpers; pick remains — red-green confirmed by temporarily restoring the `didPerformAction` call). Tagging was already correct; no change there.
