## Findings

### F1: `audioConfigured` row implies it waits for the asynchronous audio retry  (fixed)

- **severity:** Nit
- **status:** fixed
- **location:** docs/sentry-termination-diagnostics.md:196
- **concern:** The table said `audioConfigured` follows audio setup "including the asynchronous-retry fallback", but `bootstrap` records it right after scheduling that retry, so a reader could take it as audio fully configured.
- **resolution:** Reworded the row to say the milestone follows the synchronous setup, or the scheduling of its asynchronous retry when that setup fails.
- **fixed_at:** 2026-10-30

### F2: `not_retained` was undefined beyond its name  (fixed)

- **severity:** Nit
- **status:** fixed
- **location:** docs/sentry-termination-diagnostics.md:210
- **concern:** The context docs listed `not_retained` without saying it also covers launches from builds without timelines, launches killed before their first milestone, and failed file creation, not only pruning.
- **resolution:** Defined `not_retained` and listed those causes, so the first post-update crashes aren't misread as retention loss.
- **fixed_at:** 2026-10-30

### F3: The first milestone is read as pre-main, but PodHaven code runs before it  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/AppDelegate.swift:25, docs/sentry-termination-diagnostics.md:229
- **concern:** #815 planned a `didFinishLaunching` entry milestone to separate pre-main from PodHaven's launch work; the PR omitted it, and the docs read a late `loggingStarted` as pre-main, though environment setup, swift-log's bootstrap, and the timeline's own file creation run before it.
- **resolution:** The delegate captures its entry time and `configureLogging` stores it as `didFinishLaunching` right after swift-log's bootstrap, through `record(_:at:)`. The docs read that milestone as pre-main and UIKit work, and the window after it as the start of `bootstrap`.
- **fixed_at:** 2026-10-30
