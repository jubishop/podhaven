## Findings

### F1: A duration that rounds to 2^63 seconds crashes every formatter that shows it  (skipped)

- **severity:** Critical
- **status:** skipped
- **scope:** in-diff
- **location:** PodHaven/Extensions/CMTime.swift:49, PodHaven/Extensions/TimeInterval.swift:62
- **concern:** The `Double` parser keeps values such as `9223372036854775808`, which `CMTime` saturates to a numeric `Int64.max`, and `CMTime.timeComponents` and `TimeInterval.formattedParts` then trap in `Int(_:)`; `main` already stores `9223372036854775807` this way.
- **resolution:** Deferred, not fixed here: `b2892c16` removed this PR's `Int(exactly:)` formatter fix, and PR #1056 (#993) and PR #1060 (#1057) fixed the formatters before this PR merged. In PR #1056, `CMTime.timeComponents` converts with `Int(exactly:)` and returns `nil` on failure, so `description` and `shortDescription` show `Unknown` for NaN, the infinities, and times past `Int`'s range, without saturating; `CMTimeTests` covers it. In PR #1060, `TimeInterval.formattedParts` returns `nil` the same way, so `compactReadableFormat` and `playbackTimeFormat` show `Unknown`, with no minus sign, for those times in either direction, neither saturating nor formatting them as zero, while `Int.min` seconds still formats; `testUnrepresentableTimesAreUnknown` and `testIntRangeEdgesFormat` cover it. Both format in-range times as before.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/993, https://github.com/jubishop/podhaven/issues/1057
