## Findings

### F1: A parseable but non-absolute self link still breaks the feed  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Feed/Models/PodcastFeed.swift:183 (scope: related)
- **concern:** `PodcastFeed.init` converts `rssPodcast.feedURL ?? from` with no fallback, so a `/feed.xml` or `feed://` self href fails the whole feed and a bare `feed.xml` is stored as `https://feed.xml`, though the fetched URL is valid.
- **resolution:** Deferred, not fixed. The defect predates this PR, which doesn't make it worse. No production occurrence is known, and the issue's done conditions cover only empty values.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/841

### F2: Trimming changes the identity of trailing-space enclosure URLs  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Feed/Models/PodcastRSS.swift:18 (scope: in-diff)
- **concern:** Before, `url="https://x/a.mp3 "` was stored as `https://x/a.mp3%20`. It's now trimmed, so on the next refresh an item without a `<guid>` gets a new derived GUID and media URL and is inserted, and maybe auto-queued, as a duplicate of the old row.
- **resolution:** Skipped. It needs a trailing-space enclosure URL on an item with no `<guid>`, and no such feed is known. The old `%20` URL most likely never played, the harm is a one-time duplicate with no data loss, and keeping the untrimmed string would keep those broken URLs.
