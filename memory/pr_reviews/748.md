## Findings

### F1: Forwarded crash stacks are inverted  (fixed)

- **severity:** Critical
- **status:** fixed
- **location:** PodHaven/MetricKitCrashDiagnostics.swift:333
- **concern:** The converter treated each crash call stack's root frame as the outermost caller, but MetricKit roots crash stacks at the crashing frame and nests callers in `subFrames` (Apple's `jsonRepresentation()` example; sentry-cocoa's real `tree-real.json`), so Sentry would show inverted stacks, title issues after the outermost in-app frame, and truncate away the crash site.
- **resolution:** `callerFirstPath` reverses the most-sampled chain; the Swift test tree, smoke fixture, offline-order check, and docs now use MetricKit's orientation.
- **fixed_at:** 2026-10-15

### F2: Deep crash call trees are not forwarded  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/MetricKitCrashDiagnostics.swift:177
- **concern:** Foundation's JSON parsers reject nesting beyond 512 levels, so a crash tree with any thread of 255+ frames fails to decode and the eligible diagnostic is logged as an error instead of reaching Sentry.
- **resolution:** Deferred, not fixed: typical stacks forward correctly, the failure reaches Sentry Logs, and the raw record stays local; a depth-tolerant parse needs its own change.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/749
