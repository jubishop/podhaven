## Findings

### F4: Recovery reload alerts a cancelled load as an error  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+MediaServicesRecovery.swift:85-93 (scope: related)
- **concern:** When a second reset or a deletion cancels a recovery reload without changing the playback revision, `reloadMediaServicesRecoveryIfNeeded` shows an "Error" alert with the raw `CancellationError` text. The episode-list play path skips unremarkable errors, but this path doesn't.
- **resolution:** Skipped. The behavior predates this PR, which doesn't make it worse. It needs a second reset or a deletion during a recovery load, which itself follows a rare reset. A second reset's own alert likely replaces it, and the harm is one spurious alert. A cancellation guard would be cheap but is outside the PR's outcome.

### F3: Second reset during a recovery load drops the episode  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+Events.swift:205-206; PodHaven/Play/PlayManager+MediaServicesRecovery.swift:48
- **concern:** A reset arriving after a recovery load cleared On Deck read no interrupted episode, so the failed load's restore dequeued the episode and the reset then cleared On Deck. The episode was then neither On Deck nor in Up Next, and the alert named the next queued episode.
- **resolution:** `handleMediaServicesReset` falls back to `mediaServicesRecoveryEpisodeID`. `repeatedResetDuringRecoveryLoadKeepsInterruptedEpisodeOnDeck` failed before (`OnDeck is: nil`) and passes after. Residual risk: if the reset reads On Deck before the restore sets it, the alert can still name the next queued episode. The queue and Play are unaffected, and 16 runs never hit that order.
- **fixed_at:** 2026-11-02

### F2: Deleted recovery episode leaves `.paused` with nothing On Deck  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager+MediaServicesRecovery.swift:70-76
- **concern:** When Play finds the recovery episode deleted before `removeDeletedEpisodes` runs, `reloadMediaServicesRecoveryIfNeeded` clears On Deck and `currentEpisodeID` but keeps the new recovery `.paused`, and the later cleanup skips because nothing identifies the episode. The PlayBar and widgets show a paused player with no episode. That breaks #819's requirement to keep the reset deletion guarantees.
- **resolution:** The not-found branch now calls `setStatus(.stopped)` after clearing On Deck. `recoveryPlayStopsWhenInterruptedEpisodeWasDeleted` failed before the change and passes after it.
- **fixed_at:** 2026-11-02

### F1: PlayBar seek controls silently no-op during reset recovery  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager+MediaServicesRecovery.swift:36; PodHaven/Play/PlayManager+PlaybackControls.swift:9-25
- **concern:** `.paused` recovery replaces the stopped PlayBar with skip and scrub controls, but no item is loaded, so `PodAVPlayer.seek` drops every seek and the next Play resumes from the saved position.
- **resolution:** Skipped. The path is rare (a reset, then a skip before Play), does no harm, and recovers on Play. Honoring these seeks would need a new recovery-only seek branch that persists the position and changes the time source for skip forward and back. The PR's outcome doesn't need it.
