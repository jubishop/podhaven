## Findings

### F4: `playRequested(by:)` is a one-call-site helper  (skipped)

- **severity:** Nit
- **status:** skipped
- **location:** PodHaven/Play/Utility/PodAVPlayer.swift:435 (scope: in-diff)
- **concern:** `PodAVPlayer.playRequested(by:)` has one caller and repeats the inline `playbackRequestID == playbackRequestRevision` check in `handleItemStatusChange`, against the one-call-site helper rule.
- **resolution:** #957 owns merging both "playback was requested" checks into one and names this API. Inlining it now would change no behavior and would leave that plan out of date.

### F3: Failure recovery during an interruption cancels its resume  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Play/PlayManager.swift:636 (scope: in-diff)
- **concern:** `stop()` cleared `interruptedPlayback`, but its only production caller is `handlePlaybackFailure`, so an item failure recovered during an interruption that began while playing left the episode paused after a `.shouldResume` end, where `main` resumed it.
- **resolution:** `stop()` no longer clears the owed resume; deliberate `pause()` and `toggle()` still do. The red-green `.itemFailedDuring` case replaces the `.stoppedDuring` case, which only tests could reach.
- **fixed_at:** 2026-11-09

### F2: Owed resume outlives an interruption that never ends  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager.swift:693 (scope: in-diff)
- **concern:** iOS doesn't guarantee an ended notification, and only `pause`, `stop`, `toggle`, or an end clear `interruptedPlayback`, so a resume owed by an unfinished interruption survives a later play and a system pause into the next interruption.
- **resolution:** Deferred, not fixed. It has no effect today because the system pauses that could expose it already leave a play as the latest request, which #957 tracks. Added the stale-flag path, a clear-on-pause approach, and a red-green done condition to #957 so its fix covers it.
- **follow_up_issue:** https://github.com/jubishop/podhaven/issues/957

### F1: A play requested during an interruption isn't resumed  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Play/PlayManager.swift:709 (scope: in-diff)
- **concern:** The end resumes only a resume owed when the interruption began, so a play requested after it began that the system blocks during a call (a play after a pause, any toggle to play, or `loadAndPlay` finishing its load) stays paused after the call, where `main` resumed it.
- **resolution:** #878 specifies resuming only playback active when the interruption began. Pressing play mid-call is rare, one more press recovers, and resuming on the latest request at the end would add a second evaluation point and tests for no observed report.
