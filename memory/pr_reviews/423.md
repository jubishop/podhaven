# PR 423 review ledger

## Findings

### F1 — Text filter predicates used raw SQL instead of GRDB query interface
- source_thread_id: PRRT_kwDONT4Ems6HK-8u (coderabbitai)
- concern: episodeTextExpression/podcastTextExpression built LIKE predicates with raw SQL(sql:), the lone raw-SQL holdout in an otherwise pure-GRDB engine.
- status: fixed
- fixed_at: 2026-06-09
- resolution: Converted to GRDB `like(_:escape:)`, `collating(.nocase)`, `== nil`, and a `Podcast.select().filter().contains()` subquery; LIKE's built-in ASCII case-insensitivity replaces the redundant `lower()`. Parity + edge-case suites pass unchanged.

### F2 — No DB-level validation of filter JSON column
- source_thread_id: PRRT_kwDONT4Ems6INHE8 (jubishop)
- concern: smartList.filter was plain TEXT accepting any string; owner asked for DB-level validation of filter contents.
- status: fixed
- fixed_at: 2026-06-09
- resolution: Added `CHECK(json_valid(filter))` to the v51 column (migration unshipped, editable) + red-green test. Full structural validation would need EAV normalization (declined, see F5); json_valid is the available structural guard for an opaque JSON column.

### F3 — "business key" jargon unclear in SmartList comment
- source_thread_id: PRRT_kwDONT4Ems6INH-7 (jubishop)
- concern: id:Self comment used unexplained term "business key".
- status: fixed
- fixed_at: 2026-06-09
- resolution: Reworded to "An unsaved row has no database id yet, so the value is its own identity."; reply defined the term (natural/domain key vs surrogate id).

### F4 — Should displayOrder be UNIQUE?
- source_thread_id: PRRT_kwDONT4Ems6INI2d (jubishop)
- concern: displayOrder is a dense unique sequence; owner asks whether to enforce uniqueness at the DB level.
- status: pending
- resolution: Replied recommending against UNIQUE — SQLite UNIQUE indexes are not deferrable, so moveSmartList's per-row renumber hits transient collisions mid-transaction; enforcing it forces a two-pass renumber for no real gain (renumber is the sole writer, already tested). Left open for owner's call.

### F5 — Defend JSON filter storage vs structured SQL
- source_thread_id: PRRT_kwDONT4Ems6INN6f (jubishop)
- concern: owner challenges storing the filter as opaque JSON TEXT rather than a normalized schema.
- status: pending
- resolution: Replied defending JSON — the filter is a small recursive boolean tree of heterogeneous, open-ended condition kinds, always read/written/used as a whole; only tag-scrub reaches in (O(lists)). Normalizing means EAV sparse table + per-kind CHECKs + tree reconstruction + migration-per-new-kind. Shipped json_valid as the DB guard. Left open for owner decision (structured = separate effort/PR).

### F6 — Tag-scrub on delete would be cleaner with structured filters
- source_thread_id: PRRT_kwDONT4Ems6INO5D (jubishop)
- concern: Repo.deleteTag loads/decodes/scrubs/re-encodes every filter because tag IDs live in JSON (no FK cascade).
- status: pending
- resolution: Replied — this is the one place JSON costs us, but the scrub is O(lists) (few rows), in-transaction, and tested; it does not justify normalizing the whole tree. Cross-referenced F5. Left open.

### F7 — Docs drift: migration version + key-retention contract
- source_review_id: PRR_kwDONT4Ems8AAAABCBgZdA (coderabbitai, outside-diff)
- concern: docs said "v43 migration" (should be v51) and claimed old sort-pref keys are removed, contradicting the Phase 1 copy-don't-delete contract.
- status: fixed
- fixed_at: 2026-06-09
- resolution: Fixed v43→v51, aligned both lines (247, 358) to copy-don't-delete, and added the json_valid check to the doc's embedded migration snippet.
