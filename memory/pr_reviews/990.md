## Findings

### F1: Offline fetches time out and back off every healthy feed  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** PodHaven/Feed/RefreshManager.swift:275 (scope: in-diff)
- **concern:** `podcastFeedSession` waits for connectivity, so an offline fetch ends in `URLError.timedOut`, never `.notConnectedToInternet`. The PR counted that timeout as a feed failure, so time spent offline backed off every stale feed for up to 24 hours after reconnecting.
- **resolution:** `ConnectionState.Path` now reports `isSatisfied`. `RefreshManager` doesn't count a `URLError` raised while the path is unsatisfied. A red-green test in `RefreshManagerBackoffTests` shows a timeout doesn't back off a feed while offline and still does once the device is back online.
- **fixed_at:** 2026-11-09

### F2: A captive portal or DNS outage backs off every feed  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** PodHaven/Feed/RefreshManager.swift:271 (scope: in-diff)
- **concern:** On a network that is connected but has no working internet, every feed fails with an HTML parse error or a host error, and each one records a backoff.
- **resolution:** Skipped as rare. The cost is bounded: the backoff doubles only while the outage lasts, and the first success or any manual refresh clears it. A rule that ignores a pass where every feed fails would also hide the dead-feed case #912 fixes.

### F3: Failure count comes from the pass's snapshot  (skipped)

- **severity:** Nit
- **status:** skipped
- **location:** PodHaven/Feed/RefreshManager.swift:200 (scope: in-diff)
- **concern:** `failure(of:)` adds one to the row read at the start of the pass, so a concurrent `refreshSeries` result on the same feed can set the next backoff from a stale count.
- **resolution:** Skipped. It needs a detail refresh of the same feed to finish between a pass's read and its fetch. The wrong interval lasts one attempt, and the next result sets the count again.
